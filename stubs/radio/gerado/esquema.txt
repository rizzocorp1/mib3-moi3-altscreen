# Esquema dos serviços DSI do sintonizador da HMI do MOI3 (firmware MU0883, HMI H40.272.304).
# GERADO por driver/m8_esquema.sh (driver/LeEsquemaDSI.java) a partir das classes do próprio
# firmware, na JVM dele. Não editar à mão. Estudo num computador; nada daqui vai para o carro.
#
# Uma coisa por linha, campos separados por espaço:
#   S <serviço> <domínio> <interface de pedidos> <interface de eventos> <pacote da LG>
#   W <domínio> <interface org.dsi.ifc> <instância> <atraso em ms>   serviço que a HMI liga ao receber o anúncio (interface 9000)
#   A <serviço> <número> <constante ATTR_>                          atributo que a HMI pode assinar
#   E <serviço> <api> <atributo ou -> <entrega ou -> <evento> <mensagem ou ->
#        mensagem que o serviço manda. Com atributo, é a atualização dele (a api tem o mesmo número).
#        entrega: o número com que a HMI procura os ouvintes; quando difere do atributo, a
#        atualização só chega a quem também assinou esse outro (é assim no firmware).
#   P <serviço> <api> <método> <mensagem ou ->                      pedido que a HMI manda (9999 assina atributos, 9998 desassina)
#   R <serviço> <api do pedido> <tipo> <prazo em ms> <api da resposta ou -> <método do ouvinte>
#        pedido de que a HMI espera resposta, pela tabela do proxy DSI dela (Cfg.PT e Cfg.U). Uma linha
#        por resposta possível. tipo: uma = uma resposta só; escolha = uma dentre as listadas;
#        sequencia = todas; complexa = quem decide é um analisador da HMI. prazo: quanto ela espera antes
#        de registrar "DSI timeout occurred" (-1 = sem prazo). "-" = nenhuma api da camada da LG chama o método.
#   G <serviço> <api do pedido> <api do evento> <regra> <campo do pedido> <campo do evento>
#        o que o pedido set<X> grava no atributo de nome <X>, campo a campo. DEDUÇÃO do gerador: o firmware
#        não traz essa ligação. regra posicao = os campos do pedido são os do evento, número a número e
#        tipo a tipo, fora o validFlag; regra nomes = cada campo do pedido tem um só campo de mesmo nome e
#        tipo no evento (é a menos segura: conferir antes de ligar o serviço em "grava").
#   X <serviço> <api do pedido> <api da resposta> <campo do pedido> <campo da resposta>
#        o que a resposta devolve do pedido: campos de mesmo caminho e tipo nas duas mensagens. DEDUÇÃO.
#   M <mensagem>                                                    mensagem protobuf; seguem os campos dela
#   C <número> <nome> <tipo> <um|rep|pac> [<mensagem do campo>]      campo da mensagem da linha M de cima
#        tipo: sint32 e sint64 vão em zigue-zague; int32, int64, uint32 e enum, em varint comum;
#        fixed32, fixed64, bool, float, double, string, bytes; msg é outra mensagem.
#        um = campo simples; rep = repetido, um por vez; pac = repetido empacotado.
# No barramento: [canal:8][interface:4][instância:4][api:4][protobuf]. O canal é o remetente:
# os eventos saem com o domínio do serviço; os pedidos da HMI, com 0x8000.
